### 2.3 NEW ship-blocker found 2026-07-06: screenshots show the wrong Pro price ($4.99, not $11.99)

Re-viewed `APP_IPHONE_67_01.png` and `APP_IPAD_PRO_6GEN_129_01.png` (both in the "fresh, today"
set from §2.2) specifically to confirm the $11.99 Pro price required by this pass. **Both show
"Unlock NumPad Pro — $4.99"** in the CTA button and the plan-card price, not $11.99.

Root cause is already diagnosed and committed, and is explicitly **unresolved**:
`1d7ddfb9` ("fix: wire StoreKit config into scheme (price still not verified — see notes)")
attached `NumPad/Products.storekit` (which correctly declares `numpad.pro.lifetime` at
`"displayPrice": "11.99"`) to the shared scheme's Launch and Test actions, then verified via
`testSlot01_store` on a freshly erased sim, across three relative/absolute path variants, that
`storekitd` **still** reports the client running in `Sandbox` mode (hitting
`sandbox.itunes.apple.com`) and the Store screen **still** renders $4.99 — i.e., the scheme change
did not change observed behavior, and the commit message says so verbatim: *"the $4.99 root cause
is NOT confirmed fixed."* Chronologically, `7c140e69`/`ddef9484` (the screenshot captures) landed
*before* `1d7ddfb9` (the scheme-wiring attempt) — so the screenshots were captured while this bug
was already present, and the later, more thorough investigation in `1d7ddfb9` independently
confirmed the same sandbox-fallback/$4.99 behavior is still there today. Nothing between those
commits and now would have changed it.

This is consistent with §3's owner-gated item "Reprice `numpad.pro.lifetime` → $11.99 in ASC
(code/`.storekit` already reflect the target price for sim testing only — ASC pricing is
separate)" — i.e., ASC's sandbox listing for this product is still priced at whatever it was
before the 2.0 price change (evidently $4.99), and the local `.storekit` Testing config that
*does* say $11.99 is not actually being consulted at capture time.

**Why this blocks submission:** these are the literal image files staged to upload as the app's
"final" App Store screenshots. Shipping a screenshot that advertises $4.99 for a product ASC will
actually charge $11.99 for is a real-money pricing-accuracy problem for prospective customers and
a plausible App Review flag, not a cosmetic nit. It cannot be waved through as "owner-gated,
non-blocking" the way the underlying ASC-repricing task is — the *artifact* is wrong today and is
about to ship.

**Why this pass does not fix it:** the prior commit already tried three path variants for the
scheme wiring and confirmed none of them changed the sandbox-fallback behavior under
`xcodebuild`/simulator launch — the remaining root cause is deeper than a relative-path typo (most
likely either genuine ASC sandbox pricing drift, or a `xcodebuild`-vs-Xcode-GUI difference in how
StoreKit Testing configs attach to a test/launch session) and fixing it blind, without on-device
re-verification, would just be a second unverified claim stacked on the first. Recapturing the
30 en-US screenshots (plus, eventually, per-locale sets) is also outside this pass's scope (a
confirmation/verification pass, not a screenshot-pipeline debugging session).

**Required before this ship-blocker closes:** (a) get the Store screen to render $11.99 in a
live simulator/device session — either by fixing whatever is defeating the StoreKit Testing
config attachment, or by repricing the ASC sandbox listing to $11.99 so the sandbox fallback
itself returns the right number — confirmed by direct observation, not by re-reading the same
`.storekit` file; then (b) re-run the screenshot capture suite and re-verify the new PNGs show
$11.99 before upload.

Neither blocked the *binary* from building or passing tests — both were marketing-asset gaps,
now closed by content + asset commits, verified above.
