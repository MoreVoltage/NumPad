# NumPad Moonshot Council — Moat & Acquisition Logic

Date: 2026-07-03. Branch: `feat/2.0-ux-overhaul`. Research-only — no source changes, not committed.

**Lens:** why would Apple (or anyone) pay ~$20M for NumPad instead of building it themselves?
Installed-base + reviews as brand moat, B2B contracts, custom-keyboard/editor IP, cross-app
numeric-workspace lock-in (tape/clipboard/snippets synced), patentable interactions, category
ownership ("the numpad," like "the weather app").

**Grounding done before ideating:** `graphify query` passes over the custom keyboard editor/drag
component, Result Tape/Clipboard/Snippets/CloudSync, and keyboard-height/kiosk subsystems; full
read of `docs/plans/2026-07-03-pack-lineup-proposal.md`, `docs/plans/2026-07-03-b2b-validation-brief.md`,
and `docs/plans/2026-07-03-secondary-keypress-design.md`; `CLAUDE.md` for the existing feature
inventory (5 packs, 17 themes, Custom Keyboard v2 with springboard drag-reorder, iPad heights incl.
Pro-gated Kiosk 500pt, iCloud KVS sync of the custom-keyboard blob, GA Result Tape, entitlement-gated
Conversion overlay, Clipboard History, Snippets); web research on Fleksy/KeyboardKit Pro B2B SDK
pricing precedent, Apple's `FoundationModels` on-device framework (iOS 26, ~3B params, 4K context,
system-managed memory), and existing customizable/dynamic-keyboard patents (prior art check).

## The 5 ideas

### 1. NumPad Fleet — productize the B2B kiosk deployment that already works

**Pitch:** `docs/plans/2026-07-03-b2b-validation-brief.md` already concludes Product A (keyboard
extension + managed deployment) works **today, with zero new engineering** — the gap is entirely
packaging and sales process, not code. NumPad Fleet turns that into a real line item: a
configuration-profile generator that takes an IT buyer's choices (locked pack, locked theme, Full
Access on/off, height preset) and emits an Apple Business Manager custom-app config + a one-page
deployment guide, sold as per-device volume licensing with a named support contact. This is the
single highest-leverage item on this list because it monetizes an asset that is **already fully
built** — the moat isn't new code, it's the accumulated deployment playbook, the first few
reference customers, and the support relationship that a competitor starting from zero can't
fast-follow into.

**Wow moment:** "we deployed 500 iPad kiosks in three states and IT never had to touch a line of
MDM config we didn't hand them pre-built."

**Effort:** M (mostly process/config, not Swift — the console can start as a static form + PDF
generator; only real code is a couple of Remote-Config-driven kiosk lockdown toggles).

**Risk:** B2B go-to-market is a different muscle than consumer app dev; the validation brief is
explicit that there are **zero committed Product B customers** and Product A discovery calls
haven't happened yet — do not overbuild the console before at least one paid pilot confirms the
packaging (per the brief's own "open questions" section).

**Wow-per-effort: 8/10**

**First shippable slice:** a single-page kiosk-config generator (inputs: pack, theme, height
preset, Full Access on/off → outputs an `.mobileconfig`/ABM payload + the existing
`docs/kiosk/NumPad-for-Kiosks.md` content repackaged as a customer-facing PDF) and a volume-pricing
SKU in ABM — sellable before any dashboard exists.

**Not-defensible adjacent trap:** the underlying keyboard-extension tech itself (any competitor can
ship a numeric keyboard extension that also survives Guided Access/SAM/ASAM) — the moat here is
100% the deployment relationship and packaging, not the extension.

### 2. Numeric Workspace API — make Result Tape/Clipboard/Snippets an OS-level automation surface

**Pitch:** Result Tape, Clipboard History, and Snippets already live in the shared app group and
already sync via `CloudSync`'s iCloud KVS mirror — the data model for a genuine cross-app numeric
workspace already exists, it's just locked inside NumPad's own UI. Exposing it via App Intents
(Shortcuts, Siri, widgets, Live Activities) turns NumPad into the thing other automations *depend
on*: "Hey Siri, add $42.50 to my NumPad tape," a Lock Screen widget showing the running total, a
Live Activity that keeps a session's total visible while working a register. This is the clearest
instance of the "cross-app numeric-workspace lock-in" moat in the brief — once a user's Shortcuts
automations and widgets are wired to NumPad's intents vocabulary, ripping it out breaks workflows,
not just preferences.

**Wow moment:** NumPad becomes the de facto "number clipboard for the whole OS" — anything that can
trigger a Shortcut can read or write your running numeric session.

**Effort:** M — App Intents (basic) work from iOS 16+; widgets/Live Activities layer on top over
iOS 16–18. This is "put an Intents/widget face on data that already exists" (`ResultTape`,
`ClipboardHistoryManager`, `SnippetsManager` are already-built, already-tested models), not a new
data engine, and it's entirely app-side — no extension memory pressure at all.

**Risk:** Siri/Shortcuts discoverability is historically uneven (Apple's own suggestion surfacing
is a black box); widgets/Live Activities are their own App Group-aware extension targets to build
and maintain, which is incremental surface area, not a rewrite.

**Wow-per-effort: 7/10**

**First shippable slice:** one App Intent ("Add Amount to NumPad Tape") plus a small Lock Screen
widget showing the running tape total, both reading/writing the existing `ResultTape` model already
in the app group — no new persistence, no new sync plumbing.

**Not-defensible adjacent trap:** the individual overlays (clipboard history, snippets, tax/tip) are
commodity UI patterns any keyboard app can clone in a sprint — the moat is the *automation surface*
sitting on top of the synced data, not the overlays themselves.

### 3. Continuity Numpad — your iPhone becomes a wireless numeric keypad for your Mac

**Pitch:** Apple's own hardware created this need: MacBook Air/Pro without a physical numpad, and
the discontinued small-footprint keyboards, are a constant complaint from finance/accounting/data-
entry users (see the Amazon/Satechi/Macally third-party numpad-accessory market this search
surfaced — real, still-active demand for exactly this gap). Ship a "Mac Companion" mode **inside
the existing container app** (not the extension — sidesteps the 50MB/no-network constraints
entirely) that streams keypresses over the local network (Bonjour/Multipeer or plain
`Network.framework`) to a small notarized Mac menu-bar helper, which synthesizes the keystroke into
whatever Mac app is frontmost via `CGEvent` (the same mechanism third-party remote-input apps like
Unified Remote already use in production, so the approach is proven, not speculative). This
directly extends the installed-base/reviews moat into the Mac ecosystem and gives Apple a
compelling acquisition story: NumPad becomes the numeric-input answer for the exact hardware gap
Apple itself created, with App Store reviews and an installed base already validating demand,
instead of Apple building and support-owning a new continuity feature from scratch.

**Wow moment:** "type into Numbers on your Mac from the same NumPad you already trust on your
iPhone — no Bluetooth pairing, no separate $70 accessory."

**Effort:** L — the iOS side is a moderate lift (app-side networking + UI, no extension changes);
the Mac side is a **new target and a new platform** (menu-bar helper, Accessibility-permission UX,
notarization, its own support surface) — this is the heaviest lift of the five.

**Risk:** cross-device reliability is exactly the class of bug that burns trust fast (dropped
keystrokes, focus-follows-mouse edge cases); Mac App Store sandboxing may force the helper to be
a direct-download (non-sandboxed) distribution initially, which is a support/trust hurdle of its
own; genuinely new platform surface for a small team to own long-term.

**Wow-per-effort: 7/10**

**First shippable slice:** foreground-only MVP — a "Mac Companion" screen in the iOS app; tapping a
digit sends it over Bonjour to a direct-download (not yet Mac-App-Store) menu-bar helper that
injects the keystroke into the frontmost app. Ship DEBUG/TestFlight-only first to validate
reliability before investing in backgrounding, auto-pairing, or Mac App Store distribution.

**Not-defensible adjacent trap:** generic "remote keyboard/mouse" apps already exist and are not a
moat by themselves (Unified Remote, Remote Mouse) — the differentiator is that it's the *same*
numeric workspace (same tape/clipboard/snippets, same muscle memory) extending across devices, not
a bare keystroke pipe.

### 4. Ask the Number — on-device Apple Intelligence behind the "=" overlay

**Pitch:** The pack-lineup proposal is already promoting the `ConversionView` overlay (`"="` key)
to GA for Units & Conversion. Layer Apple's on-device `FoundationModels` framework (iOS 26+) behind
that same key for open-ended numeric natural language — "15% tip on 84 split 3 ways," "what's this
in binary," "round to the nearest hundred" — fully offline, no network, no Full Access, running via
the system-managed on-device model rather than anything bundled into the extension's own memory
budget. This would make NumPad the first custom keyboard extension on the App Store to genuinely
integrate Apple Intelligence, which is a real distribution moat: Apple actively curates and
features "apps using Apple Intelligence" collections, and first-mover visibility in a new App
Store category is hard to unseat even after competitors copy the feature.

**Wow moment:** "ask your keyboard a math question in plain English and watch the answer type
itself in — completely offline."

**Effort:** M/L — **contingent on a spike**. Web research did not confirm whether `FoundationModels`
is callable from within a third-party **app extension** process (as opposed to the container app);
Apple's own QuickType/predictive-text historically runs with OS-level privileges third-party
extensions don't get. This is the single biggest unknown of the five ideas and must be resolved
before any UI investment.

**Risk:** HIGH on the framework-availability question above; also gated by Apple Intelligence
device/region/language eligibility and a 4K token context window, which narrows the addressable
population regardless of the framework question; iOS 26-only requires a hard `#available` gate with
a real fallback (the existing calculator/converter) below it, not a degraded experience.

**Wow-per-effort: 8/10 if the spike succeeds; scope down hard if it doesn't.**

**First shippable slice:** a throwaway on-device spike (not user-facing) confirming
`SystemLanguageModel` availability and a basic prompt/response round trip **called from the actual
Keyboard extension target on a real device** — not the app target, since that's the case that
matters and the case most likely to fail. If the extension can't reach the model, fall the whole
idea back to a "Number Assistant" screen inside the container app only — still shippable, materially
smaller wow.

**Not-defensible adjacent trap:** a generic LLM wrapper with no proprietary data isn't defensible
tech by itself (any app can call the same public `FoundationModels` API) — the moat here is
first-mover timing/visibility and the specific integration into an already-trusted numeric workflow,
not the model access itself.

### 5. NumPad IP Portfolio — file narrow patents on the interaction mechanics already built

**Pitch:** The Custom Keyboard v2 editor already contains genuinely non-obvious, already-designed
mechanics: (a) the reserved-gesture-precedence system in
`docs/plans/2026-07-03-secondary-keypress-design.md` — a single long-press gesture that resolves to
a *different* action depending on live title/role matching against reserved system overlays vs. a
user-assigned secondary, with an explicit precedence rule; (b) the constrained, springboard-style
drag-reorder for peripheral keyboard sections with index-aligned primary/secondary parallel-array
sync and handedness-aware column mirroring (`CustomKeyboardReorder`, `Handedness`); (c) the
"selected pack supersedes the custom top row, but columns persist" layering model that lets a
static pack system and a fully custom keyboard coexist in one rendering pipeline. Filing narrow
patent/design-patent claims around these specific mechanics converts already-sunk design work into
an actual legal asset that transfers in an acquisition — a real moat beyond "we shipped first,"
which is otherwise the *only* protection this app's UI has.

**Wow moment:** an acquirer's due-diligence packet includes filed IP, not just a codebase a
motivated competitor could rebuild in a quarter.

**Effort:** S from an engineering standpoint (the mechanics are already built/designed — this is a
legal/business workstream, drafting and filing, not new code) but real dollar cost and an 18–36
month path to grant via a patent attorney.

**Risk:** MEDIUM — prior art is not clean. This session's search surfaced existing granted patents
on broadly "customizable"/"user-personalizable" and "dynamically customized" keypads (USPTO
12039570, 12008233, 9052894). Claims must be drawn **narrowly** around the specific precedence-rule
and parallel-array-sync mechanics, not the general concept of a customizable keyboard — a patent
attorney needs to validate novelty and freedom-to-operate before any filing spend, not after.

**Wow-per-effort: 6/10** — cheap in engineering terms and genuinely useful in an acquisition
conversation, but slow to pay off and not guaranteed to grant; this is a "start now for optionality"
bet, not a near-term wow.

**First shippable slice (non-code):** a 1–2 page invention-disclosure memo per mechanic, written now
while the design is fresh (the secondary-keypress doc is most of (a) already), sent to a patent
attorney for a novelty/prior-art opinion — the cheapest step that preserves a priority date without
committing to full filing cost.

## What is NOT defensible — do not overinvest here

- **Individual packs / static symbol rows** (Finance, Symbols & Science, Programmer glyph arrays,
  leftover decode-only glyphs) — trivially cloneable static text; zero engineering moat.
- **Themes/color skins** — cosmetic, no technical or legal moat, any competitor matches this in a
  weekend.
- **Unit & Cooking conversion math** (`UnitConverter`) — useful, but linear/affine unit conversion
  is a commodity calculation; dozens of free converter apps do the same math. The value is in the
  *packaging* (a converter living inside a keyboard extension), not the math itself.
- **Clipboard History / Snippets as CRUD features** — standard patterns; iOS itself is trending
  toward OS-level clipboard history, which erodes this over time rather than strengthening it.
- **Tax/Tip calculator** — ubiquitous, near-zero differentiation; every calculator app on Earth has
  this.
- **The bare long-press-for-secondary-function gesture, in isolation** — iOS's own system keyboard
  already does this for accented characters; only the *specific* reserved-gesture-precedence
  disambiguation system (idea #5a) carries any real novelty, and even that is a narrow claim, not a
  broad one.
- **The à la carte pack + Pro bundle pricing structure** — a business-model choice any competitor
  can observe and copy from the App Store listing in an afternoon; not IP, not a technical moat.
- **A generic "AI wrapper" with no proprietary data** — calling a public on-device or cloud LLM API
  is not defensible tech by itself (see idea #4's own caveat); the moat there is timing/visibility,
  not the integration code.
- **"No subscription" positioning** — a real user-trust differentiator worth keeping, but it's a
  marketing/pricing stance, not something an acquirer would pay for as IP or lock-in.
