# NumPad Moonshots — Platform Citizenship

Date: 2026-07-03. Branch: `feat/2.0-ux-overhaul`. Research-only, no source changes, not committed.
Lens: every Apple surface NumPad could own beyond the keyboard extension itself — App Intents/Siri/
Shortcuts, interactive widgets, Live Activities, Spotlight, StandBy, Apple Watch, visionOS, Handoff.

## Grounding (what already exists, verified against the codebase)

- **Zero platform-extension surface today.** `grep` for `AppIntent|WidgetKit|ActivityKit|INIntent|
  Shortcuts|Spotlight|CSSearchable|NSUserActivity|WatchKit|watchOS|visionOS` across the whole repo
  returns nothing. This is genuinely greenfield — every idea below is additive, nothing to migrate.
- **The pack lineup proposal has already shipped further than CLAUDE.md's snapshot suggests.**
  `PacksViewController.PackOption` and `KeyboardType` now include `.units` and `.cooking` as live,
  selectable packs (confirmed via graphify + `PacksViewController.swift`), and
  `UnitConverter.Category` already has all four cases including `.volume` — length/mass/temperature/
  volume conversion is a complete, tested, pure-function engine today, not a future build. This
  matters a lot for the App Intents idea below: "convert 2 cups to ml" is a today-sized wrapper, not
  a new engine.
- **Pure, dependency-free compute engines already exist app-group-wide:** `Calculator` (RPN
  arithmetic evaluator, `Keyboard/…evaluate()`), `TaxTipMath.total`/`.tipOnly`, `UnitConverter.convert`,
  `DateTimeTokens.value(for:)`. All are `enum`s with static pure functions — zero UIKit, zero
  StoreKit, zero Firebase dependency. They are the cheapest possible payload to expose through a new
  Apple surface because the "hard part" (the math) is already written and unit-tested.
- **Cross-process data already flows through the App Group, today:** `ResultTape` (last 20 computed
  results, `UserDefaults.group`), `SnippetsManager`, `ClipboardHistoryManager` (Keychain-backed,
  1-hour TTL unless pinned), `CustomKeyboardConfig`/`Handedness` (synced to iCloud KVS via
  `CloudSync` for Pro users). A widget extension or App Intent living in the container app can read
  all of this **without touching the keyboard extension's code** — the data model is already
  extension-friendly.
- **`SettingsSync` (Darwin notifications) is the existing precedent for the app ↔ keyboard realtime
  channel** — any new widget/Live-Activity refresh trigger should follow the same pattern rather
  than invent a second one.
- **Constraints reconfirmed:** keyboard extension ~50MB, no network without Full Access, no
  Firebase in the extension (analytics is app-only), iOS 16.0 floor with `#available` gates for
  newer APIs (interactive widgets need iOS 17+, Live Activities need iOS 16.1+, Dynamic Island
  needs an iPhone with the hardware + iOS 16.1+, Control Center controls need iOS 18+).

## Idea 1 — Live Tape (interactive Lock Screen + Home Screen widget)

**Pitch:** A widget — Home Screen, Lock Screen, and (for free, via the same accessory family) the
StandBy smart stack — that shows the last few entries from `ResultTape`, each with a tappable
**Copy** button (an App Intents `Button(intent:)` inside the widget, iOS 17+) so a value computed on
the numpad ten minutes ago can be copied back out from the Lock Screen without unlocking the phone
or reopening whatever app you typed it in. On iOS 16 it degrades gracefully to a static, tap-to-open
widget (no interactive button, just the last result). Refresh is close to real-time: the keyboard
extension already calls `ResultTape.shared.add(result)` on every "=" — it just needs one more line,
`WidgetCenter.shared.reloadTimelines(ofKind:)`, which is a plain WidgetKit API call, not a special
entitlement, and is callable from any target (including the keyboard extension) that imports
WidgetKit and shares the App Group. No new data model, no new compute, no new cross-process channel.

**Wow moment:** You compute a tip split in the Uber Eats app, lock your phone, and the number is
already sitting on your Lock Screen with a Copy button before you've even opened Messages to send it.

**Effort:** S
**Risk:** Low — everything downstream of `ResultTape` already exists; the only new code is a widget
extension target, a timeline provider reading the same `UserDefaults.group`, and one
`WidgetCenter.reloadTimelines` call site added to the existing `evaluateInlineExpression`/tape-write
path.
**Wow-per-effort: 9/10**

**First shippable slice:** Static (non-interactive) widget, Home Screen only, showing the single most
recent `ResultTape` entry, refreshed on a 15-minute WidgetKit timeline (no extension changes at all
yet — ship the widget target first against the *existing* data, prove the App Group read path and
App Store Connect widget review pass, then add the interactive Copy button and the
`reloadTimelines` push-refresh as a fast-follow).

## Idea 2 — Ask NumPad (App Intents: Siri, Shortcuts, Spotlight actions)

**Pitch:** Wrap the three pure-function engines that already exist — `Calculator.evaluate`,
`TaxTipMath.total`/`.tipOnly`, `UnitConverter.convert` — as `AppIntent`s declared directly in the
container app target (no separate extension process required; App Intents are automatically
surfaced to Siri, the Shortcuts app, Spotlight's action row, and the Action Button as soon as they're
compiled into the app with an `AppShortcutsProvider`). "Hey Siri, what's an 18% tip on $64 with
NumPad" or "What's 2 cups in milliliters" gets answered by voice in under a second, with zero app
launch — the intent's `perform()` calls the same static function the keyboard extension calls today.
Since `UnitConverter` already has `.volume` live (Cooking pack shipped), the conversion intent is a
today-sized wrapper, not new engineering.

**Wow moment:** You ask Siri a tip or conversion question hands-free while driving or cooking, and
NumPad answers instantly without you touching the phone.

**Effort:** M
**Risk:** Low — entirely app-side, no changes to the keyboard extension or its 50MB budget; the only
real work is App Intents parameter design (natural-language phrase matching, unit disambiguation)
and localizing the intent phrases across the existing 49-locale pass.
**Wow-per-effort: 8/10**

**First shippable slice:** One intent — `CalculateTipIntent` (amount, tip %, optional tax %) — with
one donated `AppShortcut` phrase ("Calculate tip with $APP_NAME"), tested via Siri + the Shortcuts
app. Prove the pattern once, then add `ConvertUnitsIntent` and `EvaluateExpressionIntent` as
near-identical follow-ups.

## Idea 3 — Running Tab (Dynamic Island / Live Activity)

**Pitch:** The explicit "running tape" moonshot: start a "Tab" (splitting a dinner bill, tallying a
grocery run) from the Live Tape widget or an `AppIntent`, and every number you key into NumPad in
*any* app while the tab is open appends to a running total shown live in the Dynamic Island and Lock
Screen — tap the island to see the itemized list, tap **Done** to close it out into `ResultTape`.
This is the single highest-ceiling idea in the set — Live Activities plus Dynamic Island is exactly
the surface Apple has run entire "Widgets we love" / "Apps for your Lock Screen" editorial
collections around, and "a keyboard that keeps a running total in your Dynamic Island while you type
in other apps" is a genuinely novel, screenshot-ready pitch.

**Wow moment:** You're splitting a check at dinner, typing numbers into the Notes app with NumPad,
and the running total updates live in the Dynamic Island with each keystroke — no app switching.

**Effort:** L
**Risk:** Medium-High, and this is the one honest technical unknown in the whole set: `Activity.
update()` needs to be called every time a new number is keyed, and the keyboard extension is the
only process that's actually present when that happens. Whether an `ActivityKit` Live Activity
requested by the *app* can be reliably updated from the *keyboard extension* process (both sharing
the App Group + `ActivityKit` entitlement) has no established precedent in this codebase and needs a
throwaway device spike before committing to it — third-party keyboard extensions are unusually
restricted extension points, and this would be a novel use even by Apple's own sample-code
standards. If direct extension-side updates prove unreliable, the fallback (still shippable, still
has a wow moment, just less "live") is: the extension writes each new tally entry to the App Group
and posts a Darwin notification exactly like `SettingsSync` today; the *container app*, if it's
foregrounded or gets a background-refresh tick, drains the queue and calls `Activity.update()`.
That fallback trades true instant Dynamic Island updates for "updates whenever the app briefly
wakes," which is a materially smaller wow but a much safer bet.

**Wow-per-effort: 7/10** (the ceiling is a 10; discounted for the unresolved spike risk)

**First shippable slice:** Skip live continuous updates entirely for v1. Ship a **manual** Tab: user
taps "Add to Tab" as an interactive widget button (reusing Idea 1's App Intents plumbing) after each
number, which runs entirely in the app process and updates the Live Activity synchronously — zero
extension-side ActivityKit risk. This alone proves the Live Activity UI, the tab lifecycle, and the
Dynamic Island layout; automatic in-extension updates become a v2 spike once v1's plumbing is proven.

## Idea 4 — Spotlight-Native Snippets & Conversions

**Pitch:** Index the user's saved `Snippet`s (title/text, already a `Codable` model with dynamic
`{date}`/`{time}`/`{clipboard}` token expansion) as `CSSearchableItem`s via Core Spotlight, so typing
"invoice" into system-wide Spotlight search surfaces the user's "Invoice due {date}" snippet directly,
with a tap-to-copy action — no need to open NumPad, find Snippets, and scroll. Pair it with donating
`NSUserActivity`s for the app's own conversion/tax-tip screens so Siri Suggestions on the Lock Screen
and in Spotlight learn to proactively surface "Convert units" or "Calculate tip" at contextually
likely moments (e.g., after opening a receipts app), the same proactive-suggestion mechanism Apple
uses for its own apps.

**Wow moment:** You start typing "inv" in Spotlight and your own saved invoice snippet shows up
before you've even opened NumPad.

**Effort:** S–M
**Risk:** Low — entirely app-side (`CSSearchableIndex`, `NSUserActivity`), reads the existing
`Snippet` model unmodified; the only new work is index maintenance (re-index on snippet add/edit/
delete, which already has a single CRUD chokepoint in `SnippetsManager`).
**Wow-per-effort: 7/10**

**First shippable slice:** Index snippets only (skip the `NSUserActivity` proactive-suggestion half
for v1 — it's a "nice to have" layered on top, with much less certain payoff since Apple's
suggestion-ranking heuristics are a black box). Re-index on every `SnippetsManager` mutation; verify
with a real Spotlight search on device before considering it done.

## Idea 5 — Wrist Tally (Apple Watch companion)

**Pitch:** A standalone watchOS app — not a mirrored keyboard extension (Watch has no custom-keyboard
extension point) — that's a minimal tap-count tally counter plus a tax/tip quick-calc screen
(reusing `TaxTipMath` compiled into the watch target, since it's a dependency-free `enum`), synced
back to the iPhone's `ResultTape` via `WatchConnectivity` (the Watch has no App Group access to the
iPhone's container, so this needs its own transfer mechanism — `WCSession.transferUserInfo` is the
right primitive, queued and delivered even if the phone app isn't foregrounded). A server closes a
table, taps the subtotal and tip percentage on their wrist without pulling out their phone, and it's
waiting in NumPad's tape when they do.

**Wow moment:** You calculate a tip entirely on your wrist — no phone required — and it's already in
your tape when you check your phone later.

**Effort:** L
**Risk:** Medium — a genuinely new target (watchOS app + WatchConnectivity plumbing + a
from-scratch, watch-sized UI), and watchOS's stricter memory/battery budget and independent
lifecycle mean this is the least code-reuse-heavy idea of the five (only `TaxTipMath` ports
directly; everything else — UI, session handling, complication — is new). Complication support
(the watch face glance) needs `ClockKit`/`WidgetKit-on-watchOS` depending on target watchOS version,
another small API-surface decision to make explicitly.
**Wow-per-effort: 6/10**

**First shippable slice:** No sync, no complication — a single-screen watch app with a tip
calculator (amount dial + tip % stepper, both native watch input idioms) that only *displays* a
result on the wrist. Prove the target builds, ships, and passes review before adding
`WatchConnectivity` to push results back to the phone's tape.

## Surfaces considered and deliberately not in the top 5

- **visionOS:** a numeric-keypad utility has no meaningful spatial-computing story — there's no
  "why would I want this in 3D" answer, and the audience overlap (visionOS owners who need a numeric
  keyboard extension) is close to zero today. Revisit only if visionOS ever gets third-party custom
  keyboard extension support (it currently doesn't) or if the container app itself needs a
  presence there for unrelated reasons.
- **Handoff between iPhone/iPad:** `CloudSync` already gives Pro users cross-device continuity for
  settings/snippets/config via iCloud KVS — the incremental value of *also* wiring `NSUserActivity`
  Handoff on top is real but small (it would mostly save "which device has my latest snippet"
  friction that CloudSync's eventual-sync already resolves within seconds), so it scores below the
  five above on wow-per-effort. Worth a half-day add-on to Idea 4's Spotlight work later, not a
  standalone moonshot.
- **StandBy** isn't a distinct idea — StandBy's third-party surface *is* the `accessoryRectangular`/
  `accessoryCircular` widget family from Idea 1's Live Tape; there's no bespoke full-screen StandBy
  API third parties can target beyond the same widget families that already serve Lock Screen.
  Shipping Idea 1 automatically buys the StandBy smart-stack slot for free.

## Why these make Apple pick you for editorial

Apple's own seasonal collections ("Widgets We Love," "Apps for Your Lock Screen," "Get More Out of
Siri," "Great Apple Watch Companions") map almost one-to-one onto Ideas 1, 2, 3, and 5 respectively —
these aren't hypothetical categories, they're recurring, named App Store editorial slots that
specifically reward exactly this kind of platform depth on top of an otherwise-narrow utility. A
numeric keyboard is an easy category for an editor to overlook; a numeric keyboard with a genuinely
live Dynamic Island tab, an instant Siri answer, and a watch face is a much easier one to write 200
words about.

## Suggested sequencing (not a commitment — moonshot framing only)

1. Idea 1 (Live Tape) first — smallest effort, proves the widget-extension target and App Group
   read path other ideas build on.
2. Idea 2 (Ask NumPad) second — independent of Idea 1, all app-side, highest wow-per-effort after it.
3. Idea 4 (Spotlight) as a cheap parallel track — no shared code with 1/2/3, can slot in anywhere.
4. Idea 3 (Running Tab) only after a dedicated device spike resolves the extension-side ActivityKit
   update question; its manual-tab v1 slice can start any time but shouldn't be scoped as "done"
   until the live-update question has a real answer.
5. Idea 5 (Wrist Tally) last — largest net-new surface area, most independent of the other four,
   best done once the phone-side platform work has already established the App Intents/WidgetKit
   patterns this can partially mirror.
